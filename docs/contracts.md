# Additive managed event contracts

The managed core provides dependency-free contract values, available from `modkit_events` and the explicit `modkit_events.contracts`, `.subscriptions`, and `.delivery` modules. Optional Pydantic validation is an explicit adapter import with the `pydantic` extra. The legacy Event, JsonCodec, Dispatcher, Consumer, Redis and SQLite interfaces retain their bytes and behavior. Source/control results do not qualify a managed runtime or durable processing.

## Registration and validation

Build an immutable `ContractRegistry` from keyword-only `EventContract(name=..., schema_version=..., route=..., validator=...)` values. Each validator implements synchronous `validate(payload) -> None`. Registration duplicates always fail, even when identical. Versions of one name must share one route; different names can share a route. Lookups are exact, without case folding or schema fallback. `get`, `route_for`, `contracts`, `capabilities`, and `validate` provide access. Missing names raise UnknownEventName; absent versions of known names raise UnsupportedSchemaVersion.

Schema versions remain positive Python integers, bool excluded. No int4 or decimal-string capacity limit applies to these logical types. Codec serialization and future persistence admission have their own independent limits. A schema-validation capability is not proof of an executable handler or backend capability.

Event payload is already an immutable JSON snapshot. Validators return exactly None, never a replacement model. PayloadValidationError is the intended invalid-payload signal; arbitrary application exceptions and cancellation/SystemExit/KeyboardInterrupt propagate unchanged and may contain secrets. Non-None results are InvalidValidatorResult. Directly detectable coroutine/async-generator validators, including callable-object `__call__` methods, are configuration errors; disguised awaitable results are never awaited or scheduled. Only native coroutine results observed in inspect.CORO_CREATED (unstarted) state are closed for warning cleanup, without starting their body. Suspended, running and closed coroutines remain caller-owned and are rejected without closing or resuming them; arbitrary awaitable methods are not invoked. Callers must not concurrently manipulate a returned coroutine during synchronous validation. Validators must be deterministic, nonmutating and side-effect-free; the library cannot freeze closures or stop user code's external effects.

## Subscriptions

`Subscription(subscription_id=..., group=..., route=..., event_names=..., start_position=...)` snapshots a nonempty exact name filter. `matches(event)` filters only names, not versions. `validate(registry, handler_capabilities=...)` requires exact tuple[str,int] pairs, one or more per subscribed name, no duplicate/out-of-filter/unknown pairs and matching routes. Strings, lists and pair-like subclasses are not capability tuples. Registry keys and actual worker handler keys remain distinct; the later worker supplies actual capabilities and checks store compatibility.

`validate_subscriptions` rejects duplicate stable IDs and shared (route,group) pairs. Replicas share one manifest entry/group; independent subscriptions have distinct IDs. A subscription has one route; use multiple distinct subscriptions to compose routes/effects. Name-only filtering allows well-formed future versions to reach a later durable blocked_schema path rather than being run through an older validator. These types do not implement that durable path.

StartPosition.BEGINNING is default; LATEST must be explicit and applies only when later code creates a new group. No existing cursor may be reset automatically. These constructors never create or reset groups.

## Fixed initial managed-profile bounds

Configuration names/IDs/routes/groups/consumers are nonblank strict UTF-8, at most256 encoded bytes, without NUL. Values are not trimmed or normalized. Broker message IDs have a separate512-byte bound; canonical Redis unsigned64 millisecond/sequence IDs fit within41 ASCII bytes. Redis itself permits broader identifier forms; this is a deliberately bounded text-only managed profile, not a server limit. Delivery counts are None if genuinely unavailable or exact positive ints through2**63-1; they are never business attempts.

Registry registrations, supplied capability pairs and manifest entries are limited to4096 each; filters to1024 names. Iteration stops at the first excess item. These fixed deployment safety limits bound startup memory/work, not measured throughput or recommended service size. A future larger profile requires explicit agreement, not per-replica silent tuning. Reason tokens use at most64 ASCII bytes and must carry an application-selected category, never arbitrary exception text. Format validation does not semantically redact sensitive alphanumeric text; choosing safe categories remains application owned. These bounds DO NOT apply to legacy Event identity/name/metadata, codec configuration or DeliveryRecord.event_id.

An actual broker receipt outside these limits must be rejected without truncation, guessed count, ACK, execution or a false quarantine claim. Future managed runtime must leave source pending, mark intake unready and pause under a bounded recovery policy, not hot-loop. Durable overflow retention requires a separately qualified path. This source only validates values; real adapter/runtime overflow behavior is unimplemented.

## Delivery and phase-scoped outcomes

DeliveryContext requires actual subscription/broker/destination/group/consumer/message identity and explicit aware received_at; no clock or count defaults are fabricated. Aware times normalize to UTC. `validate_subscription` checks exact ID/destination/group consistency, not cryptographic provenance. Do not trust metadata to supply actual broker identity.

DispositionKind has CONFIRMED, REJECTED, DEFERRED, QUARANTINED, UNCERTAIN. CONFIRMED has no reason/schedule; others require an ASCII reason token; only DEFERRED can carry an optional aware retry_at. UNCERTAIN grants no automatic retry. DeliveryRecord requires event_id, DeliveryPhase and Disposition; INTAKE/PROCESSING require context, PUBLICATION may omit it. A confirmed intake is not business completion. Record construction proves no durability, authorization, replay safety or commit success. No record ACKs, retries, commits or calls services.

The distinct legacy `adapters.redis.Delivery(message_id, raw)` is unchanged. Raw replay evidence and canonical identity belong to future persistence, not these diagnostic records. Event.metadata remains arbitrary legacy JSON. Recommended keys source, occurred_at, correlation_id, causation_id, tenant_ref and trace_context are conventions only; existing trace/unknown keys remain untouched. Tenant reference is not authority. Never inject transport attempts or message IDs into business identity.

## Dependency and qualification limits

Pure import graph is contracts -> models, subscriptions -> contracts/models, delivery -> subscriptions. No workers, persistence, optional drivers or Pydantic imports. New data classes are frozen; registry private maps and filters are immutable snapshots, not guarantees against deliberate Python object internals bypass or mutable validator behavior.

Install the optional extra with `pip install "modkit-events[pydantic]"`, then explicitly import `PydanticPayloadValidator` from `modkit_events.adapters.pydantic`. The extra requires `pydantic>=2.14,<3`; the current focused source checks use Pydantic2.14.3/pydantic-core2.50.4 on Python3.12.3. This is exact source-test evidence, not an installed wheel, full dependency lock or all-platform compatibility claim.

`PydanticPayloadValidator(Model)` requires a concrete BaseModel subclass and snapshots its synchronous `model_validate` entrypoint once. It passes the same immutable Event payload directly to that entrypoint and accepts only an instance of the selected model (subclasses allowed), discarding parsed output. Event identity, payload and metadata never change. Normal nested models/dict/list schemas accept the frozen mapping proxies/tuples under the tested default configuration; a strict list schema rejects the frozen tuple. Schema strictness/coercion/extra policy and correctness of application model overrides remain application owned. A model override can lie about performing validation; the adapter cannot prove its semantic honesty.

Only Pydantic ValidationError is sanitized into a fresh fixed-message PayloadValidationError. Its cause/context/notes and framework/input fields are absent, including when invoked inside a caller's active except block. The adapter raises after leaving its private framework-error handler, then explicitly detaches implicit ambient context before bare reraising. Fixed text or `from None` alone does not establish this boundary. Traceback frame locals and application-held objects may still contain input; no whole-process erasure or safe traceback-local serialization is promised. Do not expose raw tracebacks/locals as public diagnostics.

Pydantic converts user validator ValueError/AssertionError to ValidationError, so these become sanitized invalid-input errors. TypeError/RuntimeError and uncaught cancellation/BaseException propagate by identity. Bad model return values fail InvalidValidatorResult with fixed text. Detectable asynchronous entrypoints are rejected at construction. Disguised foreign awaitables/async generators and started native coroutines are rejected without scheduling, awaiting, advancing, closing or cancellation; only native CORO_CREATED objects are closed without starting their body. The same caller nonconcurrency precondition applies.

Startup must construct registries/manifests, check actual handler exact capabilities, backend-supported persisted versions and explicit transaction/resource ownership before acquiring resources. These pure constructors implement only their own value/manifest checks; a runnable startup orchestrator, Worker settings/handler registry and adapter/lifecycle validation are separate unfinished requirements. Never use schema capabilities alone as execution or transaction authority.

Focused source checks cover pure contracts, the optional adapter, legacy async dispatch/consumer behavior, blocked optional/sibling imports, additive exports, lint and typing. Earlier legacy Redis evidence does not qualify managed delivery. Managed PostgreSQL/Redis qualification, installed wheels/sdist, combined sibling/application integration and the runtime/platform matrix remain separate gates. Shared persistence/lifecycle and worker runtime are separately owned unfinished scopes. Passing these focused controls does not complete milestone A–O.
